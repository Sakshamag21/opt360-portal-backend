Overview

Operator360 monitors the field agents ("operators") who run Aadhaar biometric enrolment and update stations. Domain fingerprints are everywhere in the code: enrolment_eid, session_operatorid, bio_dev_snum, RO/EA/UC terminology, alert routing to @uidai.net.in. Every operator gets a continuously-updated risk_score assembled from dozens of behavioral signals — odd-hour submissions, device/machine hopping, biometric fraud-check verdicts, document QC failures, parallel enrolments — which in turn drives a risk bucket, real-time Kafka signals, and (for the worst offenders) an automated suspension case.

Everything runs as Apache Airflow 3 DAGs over Trino/Iceberg tables fed by a Flink streaming layer, with the heavier scoring stage executed as PySpark jobs on Kubernetes. Because Kubernetes pods can't easily use Airflow's XComs, cross-DAG state — task status, idempotency markers, audit logs, retry bookkeeping — flows through a shared Ceph S3 bucket instead. Final results land in MySQL (the operator master record) and are served to BI/UI tooling through ClickHouse.

The codebase exists in two parallel, simultaneously-live generations — v1 and v2 — covered throughout this document and summarized in §08.

Note

Several files hardcode plaintext credentials (Ceph S3 keys, MySQL passwords, a ClickHouse password), the same pair reused across roughly 15 files. This document does not repeat those literal values — see utils/s3_audit_logger.py and siblings directly if needed.

01

The three-layer pipeline

A category only advances if it fully passed the layer before it. risk_score itself only computes when all five category scores succeeded in the same run.

02

Orchestration — the controller

operator_dag_manager.py / _v2.py run no business logic themselves — they trigger the six Layer-1 DAGs, wait, judge pass/fail per category from S3-reported task status, then cascade into Layer 2 and Layer 3.

v1 — controller_pipeline

  • Hourly tick (0 * * * *). Every tick triggers all six Layer-1 DAGs; each internally gates itself by cadence (hourly features run every tick, daily/weekly features only on the promotion tick).
  • Promotion hour = 17:00 IST. Only on that one daily tick does the controller judge Layer 1's results and, if anything passed, cascade into Layer 2 → Layer 3.
  • generate_daily_report writes a full per-category, per-layer status report to S3, including a direct query against features_risk_v1 to confirm risk_score rows actually landed — because a Layer-3 pod can report “success” purely from its shell exit code while writing nothing (see the bug in §05).
  • Structural limitation: a category that fails the 17:00 tick is done for the day — later hourly ticks still run Layer 1, but judgement and Layer 2/3 stay skipped until tomorrow.

v2 — controller_pipeline_v2: retry until midnight

Entirely separate dag_ids throughout, so v1 keeps running untouched. Promotion hour moves to 10:00 IST, and a failed category is no longer a dead end for the day.

Mechanism

The Layer-1 retry doesn't re-trigger a whole new DagRun — it clears only the specific failed task instances on the original run (only_failed=True) so already-succeeded features aren't re-inserted. It's the Layer 2/3 cascade that can't be this precise: risk_score's task only fires when all 5 category-score tasks complete within the same DagRun, so a recovered category forces a brand-new run covering every valid category, not just the new one.

03

Layer 1 — Feature computation

Six category DAGs share one design: a FEATURES dict per category, a stack of decorators around a shared runner, and a central metadata registry that turns generic SQL templates into dozens of differently-named features.

04

Layer 2 — Instance scoring

Layer 2/3 are not plain Airflow tasks — each is a Kubernetes pod that downloads a driver script from Ceph S3 and runs it via spark-submit. The files in this repo are the source-of-truth copies uploaded to S3, not what Airflow executes directly.

instances_main.py resolves (feature_name, feature_version) against the registry to get a source_table and a scoring_method name, then dynamically dispatches into one of six functions:

FunctionMechanism
rank_scoringPercentile rank of feature_value across all entities, linearly mapped into a configurable range.
winsorized_zscoringCaps outliers at the 99th percentile, z-scores, squashes through a sigmoid; extreme outliers forced to 0.99.
zscorePlain population z-score; stddev floored to 1.0 to avoid divide-by-zero.
log_based_scoringlog1p(value) / log1p(global_max), scaled into a range — compresses long-tailed counts.
wilson_fraud_scoringWilson score lower bound (95% CI) on a ratio pair (e.g. failures/total) — statistically conservative for low-volume operators.
exponential_decay_scoringTime-decayed weighted sum over a lookback window, min–max normalized.

~25 instance features feed this DAG, mostly paired score/z-score variants across auth · hardware · sustxn · work · bio. document_category_score is also computed here directly — document has no separate instance-scoring step of its own.

05

Layer 3 — Category & combined scoring

Six tasks: five <category>_category_score jobs, gated so a task simply doesn't run if its category wasn't valid coming out of Layer 2, plus one final risk_score job. In v1, risk_score explicitly depends on all five category tasks via Airflow >>; v2 drops that explicit dependency, relying only on serialized execution plus the category/idempotency gates.

The same three combination functions serve both purposes — combining instance scores into a category score, and combining category scores into risk_score — chosen per feature row via registry metadata, not hardcoded per category:

FunctionMechanism
weighted_averageΣ(value×weight) / Σ(weight) — plain weighted mean.
softmax_scoringBlends a softmax-weighted average (large values dominate more) with the plain weighted mean, 90/10 by default — lets one severe signal push the score up disproportionately.
max_scoringThe maximum feature value among the weighted set that day — “worst signal wins.”
Bug

scoring_methods/category_main.py hardcodes feature_name='document_category_score' and feature_version=1 immediately before its registry lookup — overriding whatever head_combined_risk_scoring.py actually passed on the command line (the real CLI-parsing block is present but commented out). As checked into this repo, every Layer-3 task potentially scores the wrong registry row, which can exit 0 while writing nothing or writing the wrong thing. This is exactly what the controller's _check_risk_score_data_written() daily-report check (§02) exists to catch.

Output everywhere is a numeric feature_value rounded to 2 decimals — no tier or bucket is assigned at this layer. Tiering happens downstream, in §06.

06

Serving layer & downstream

opt_master — the operator master record (MySQL)

mndc/opt_master_updt_dag.py runs daily at 9 AM as a strict 7-task chain:

  1. update_operator_metadata

    Joins UID-master tables to populate name/phone/email/RO/EA/registrar — only fills currently-NULL/Unknown fields.

  2. update_activeness

    Syncs is_active from the UID-master user status.

  3. update_risk_score

    Reads risk_score_v3, computes the percentile-rank risk_bucket, upserts into opt_master.

  4. update_sync_details / update_operator_sync_location

    Pulls device-sync and GPS events from two sources, converts DMS coordinates to decimal degrees, writes a MySQL spatial POINT.

  5. update_top_anomaly

    Across 14 known anomaly codes, picks the single highest-scoring one per operator — the “primary reason this operator is risky” field.

  6. update_opt360_features

    Mirrors the Trino feature registry into a MySQL copy.

  7. general_update

    Small cleanups: normalize “New Delhi”→“Delhi”, trim whitespace IDs, re-resolve any operator still stuck at ro=Unknown.

mndc/last_pkt_timesatmp_dag.py separately updates opt_master.last_packet_timestamp — but only if a companion S3 summary from pkt_store/opt_store.py's prior run reports SUCCESS.

ClickHouse serving layer

opt360_clickhouse_feature_store

Daily 1 PM. For every PROD feature × every risk bucket, materializes the freshest per-entity feature values into opt360_feature_store_test_v1 for fast UI lookup.

operator_risk_analysis_to_clickhouse

Daily. Cross-checks MySQL's risk_score against the max of the 6 Trino category scores (≤0.1 tolerance) before publishing to risk_analysis. Rows failing the check are silently dropped, not flagged.

opt360_clickhouse_anomalous_packet_store

Daily 1:30 AM. Six hardcoded Trino queries pull yesterday's flagged packets across categories into anomalous_packets_v3_dist — raw evidence for investigators, not aggregate scores.

Packet stores, signals & suspension

  • Packet stores (pkt_store/) push operator↔packet mappings into an external key-value store via HTTP batch-ingest — not Trino/MySQL — with opt360_packet_store triggering operator_eid_store on completion.
  • signal_mechanism/signals_producer.py is the shared library behind every signal-enabled feature: looks up active signal configs, finds entities crossing a threshold, pushes JSON events to Kafka. Warning/monitor-type signals compute an upper bound too, so only a specific value band triggers.
  • opt_suspension_dag.py consumes OPT360.SIGNALS.V1, reacting to 7 known signal ids (biometric finger/toe-print fraud, QC DOE1/POP, face non-human/POP, iris swap/flipped). For a still-active operator, it emits a structured CASE_DISPOSITION event recommending SUSPEND — a high-confidence signal can trigger suspension without human review.
  • opt360_checking_report.py emails a daily PDF ops-health summary — feature status counts, zero-row features and their last-updated date, signal/suspension counts — the human-facing counterpart to the controller's machine-readable S3 reports.
07

Standalone pipelines

opt360_parallel_transactions_eid_updt

Daily 7:30 AM. A Trino MERGE detecting operators running overlapping enrolment sessions (same operator+machine+station+client version, overlapping time ranges), upserting into txn_parallel_enrl_v1 — the table the sustxn parallel-enrolment features later aggregate. Supports ad hoc backfill via dag_run.conf.

uc_isp_data_enrichment

Daily 2 AM. Enriches UC IP addresses with ASN/carrier via a local MaxMind GeoLite2 database over a rolling 3–28-day window, clearing and re-inserting each day's partition for idempotency, writing to uc_machineip_isp_map — the table the work ISP-change feature reads.
